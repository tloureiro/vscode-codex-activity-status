# Integration investigation and design

Integration investigated on 2026-10-18. This extension uses the official Codex IDE extension's existing app-server connection; it does not modify another extension's source or start a second monitoring app-server.

Tested versions: VS Code 1.142.0; official `openai.chatgpt` 26.1007.21434 for darwin-arm64; its bundled `codex-cli` 0.162.0-alpha.17.2. Generated schemas from that bundled executable were inspected, particularly thread status, turn lifecycle, resolved requests, and blocking input. Schema generation did not start a model session.

## Evidence and choices

- [Official Codex IDE developer settings](https://learn.chatgpt.com/docs/developer-settings?surface=ide) documents `chatgpt.cliExecutable` and explicitly identifies it as development only. The installed manifest scopes it to the application and restricts it in untrusted workspaces. There was no contributed cross-extension activity API. Treat the proxy route as experimental, and recheck it on upgrades.
- [App-server protocol](https://learn.chatgpt.com/docs/app-server) documents stdio JSONL, turn lifecycle/outcomes, thread status, blocking approval/input requests, and request resolution. The observer reads that existing connection, not a separately started app-server. It injects no requests, alters no messages, approves nothing, and does not scrape the webview or parse private extension bundles.
- [Hooks](https://learn.chatgpt.com/docs/hooks) are unsuitable as the sole detector here: `Stop` can cause continuation, a `PermissionRequest` can be handled by another hook before user interaction, and hooks do not provide the required window identity. No hooks are installed.
- [VS Code theme colors](https://code.visualstudio.com/api/references/theme-color) include full status-bar, debugging/no-folder, and active/inactive title keys. [Settings scopes](https://code.visualstudio.com/docs/configure/settings) persist these values globally or at workspace scope. A global override would couple projects; a shared workspace override would couple duplicate windows. The extension therefore uses the current window’s existing folder/workspace settings, never global appearance settings. Different projects/worktrees or different saved workspace files can remain independent. If participating windows share the exact appearance settings file, all pause full-bar coloring while per-window tracking continues. No wrapper or new window is required. An unmonitored duplicate can still display shared file changes; that cannot be prevented with the public appearance API.
- [VS Code public API definitions](https://github.com/microsoft/vscode/blob/main/src/vscode-dts/vscode.d.ts) expose `window.onDidChangeWindowState` and selection events with `Keyboard`, `Mouse`, or `Command` origins. There is no general click/keystroke observer for the full application. Only real unfocused→focused changes and Keyboard/Mouse editor-selection events are automatic acknowledgement signals. The `WindowState.active` property is a coarse activity/idle signal, not a reliable event for each click; timer-driven inactivity events must not acknowledge. The finished status item directly invokes the acknowledgement command as a one-click fallback. No proposed APIs or key interception are used.

## Modules and identity

`proxy.js` tees the IDE’s existing bytes to/from the real bundled executable. `protocol.js` turns selected protocol messages into minimal events. `bridge.js` associates a direct parent PID with one UI extension host, authenticates the local socket connection using a random token, routes events independently of appearance-file identity. `color-lease.js` coordinates shared appearance-file detection across participating windows. `state.js` owns per-connection/per-thread turn and unread state. `appearance.js` applies/restores colors through the supported configuration API. `watchdog.js` performs journal recovery after a host crash. `setup.js` detects missing/stale setup, guides profile bridge configuration in the existing window through one user action, and distinguishes a missing connection from active monitoring. `extension.js` wires configuration, commands, events, and setup together.

The launcher uses shell `exec`, preserving the IDE extension host as the proxy’s direct parent. On activation, this extension writes a mode-0600 registration for its own PID in a checked mode-0700 per-user temporary directory. The proxy only looks up its direct parent’s registration. It does not walk arbitrary ancestor processes or search by cwd. A non-IDE CLI invocation has no matching parent registration and cannot color a window. Codex must be in the same local extension host as this extension; split hosts/remote environments fail to disconnected rather than falling back to project routing.

A random source identity is assigned to every authenticated socket. Window reloads replace registrations/tokens and lose old unread state. Disconnection removes that source. Reconnection snapshots only live work, never historical success. Every snapshot and incremental message is ordered on one socket. Completed turn IDs are retained in a bounded duplicate suppression set; a delayed completion for another active turn is ignored. A new request gets a provisional pending entry, so a rejected submit cannot erase an existing running turn. No transcript polling, Codex process scanning, or idle-to-completion heuristic is used. Per-thread state is capped at 1024 threads per source and duplicate suppression at 2048 ended turns.

The local socket carries only lifecycle kind, thread/turn/request IDs, outcome, and waiting flags. Conversation content traverses the original stdio connection as required by Codex; the observer briefly buffers JSON messages in memory, bounded at 8 MiB per line, and does not persist content. Oversized lines cause monitoring to disconnect while byte forwarding continues. Socket output backlog beyond 1 MiB similarly stops observation. Same-user malicious processes are outside this local token’s security boundary; the token primarily prevents accidental/mismatched connections. There is no network listener or external service.

## Appearance ownership and limits

The status-bar palette overrides `statusBar.inactiveBackground` as well as `statusBar.background` and the debugging/no-folder variants. VS Code 1.142's [status-bar rendering](https://github.com/microsoft/vscode/blob/6d62b1d5dace93a33b3a6d3eca1317bd5e15bcb1/src/vs/workbench/browser/parts/statusbar/statusbarPart.ts#L661) selects the inactive theme background when focus leaves a normal project window. Overriding only the active color therefore hid an unread completion without acknowledging it. The inactive override uses the same activity color and participates in the same ownership journal, including preservation/restoration of original theme-specific overrides. Older VS Code versions that do not recognize this color key ignore it.

The current settings target is the canonical filesystem path to `.vscode/settings.json` for a single-folder window, or to the existing `.code-workspace` for a saved workspace. It is distinct from window/host and Codex thread identity. No workspace wrappers are generated or project-reopening commands invoked. Empty/untitled multi-root workspaces need saving first.

Each participant writes a private temporary registration for that appearance file. Directory events detect peers; when native filesystem watches are unavailable, a 500 ms directory-mtime watch provides a fallback. A bounded once-per-second scan of that same tiny registration directory also reconciles dropped events and dead participants. No project scanning occurs. More than one live participant pauses colors in all participants and restores the current overlay. Symlink aliases resolve to the same key. Dead hosts are removed only after any surviving watchdog has finished recovery. Participation does not cover windows without this extension or other runtime directories. The initial activation/detection period is not atomic with VS Code rendering, so a newly opened shared-settings window can briefly display a previously persisted overlay. This exact-duplicate-window limit is explicit, and the extension no longer imposes a new-window workaround.

The journal records original existence/value and applied value per owned key, including inherited theme-specific block names. Settings writes are serialized with only the latest waiting appearance retained, so acknowledgement cannot queue behind obsolete highlights. A disk/cache mismatch retries at 50 ms intervals up to eight times, without needing another interaction, and then reports a synchronization error. On restoration, only still-owned values are reverted; unrelated keys and externally changed owned values survive. The journal is written before applying the overlay and retains previous applied values to cover a crash during a palette transition. Journals are outside the project in the checked temporary runtime directory, tagged with their owning registration token. A second window cannot restore an active owner’s journal. A watchdog starts before monitoring and restores after host IPC loss. Semantic comparison ignores JSON property order. Settings-file/cache disagreement delays overlay capture until a configuration event or bounded retry reconciles them, avoiding adopting a departing window’s color as the user baseline. VS Code may briefly display persisted colors before startup recovery, and no supported API can guarantee restoration if both processes are forcibly killed. File recovery preserves JSONC comments and unrelated settings, but cannot safely operate on invalid JSONC.

Setup does not change title-bar style. Users selecting title-bar coloring need the standard macOS custom-title-bar setting. Activity highlights temporarily modify existing workspace appearance settings; these may appear as local Git changes while active. Settings file structure and unrelated keys/comments are retained during crash recovery. No live event is inferred from app-server existence alone: a connection with no turn events is idle; a missing connection is unknown. Explicit successful turn completion is the sole source of new unread state. Async questions (`isBlocking: false` in the installed schema) are excluded even though they share the request method with blocking input.

Diagnostics keep up to 80 focus/state/appearance events and 30 appearance timing entries in memory. Entries contain counts, outcome, focus state, retry counts, and elapsed times; they exclude thread identifiers and conversation content. Focus acknowledgement remains synchronous in the state machine. Actual full-bar restoration waits for VS Code’s asynchronous configuration update and repaint. No grace-period auto-acknowledgement is applied to a completion that arrives after focus has returned.

The existing authenticated socket also accepts a read-only diagnostics handshake. These clients are never registered as activity sources, and further messages on a diagnostics connection are ignored. `node scripts/diagnostics.js` queries live registered hosts concurrently, with bounded response size and timeouts. It reports unsupported old hosts explicitly rather than misrepresenting them as healthy. The GUI diagnostics command uses the same snapshot provider. Snapshots include the owning workspace and PID so output from different windows cannot be confused; automatic focus acknowledgements asynchronously record peer focus snapshots to expose contradictory focus reports. This instrumentation does not itself alter acknowledgement policy. It established that the reported cross-window disappearance was an inactive-color rendering problem, fixed in the palette.

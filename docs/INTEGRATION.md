# Integration investigation and design

Integration investigated on 2026-10-18. This extension uses the official Codex IDE extension's existing app-server connection; it does not modify another extension's source or start a second monitoring app-server.

Tested versions: VS Code 1.142.0; official `openai.chatgpt` 26.1007.21434 for darwin-arm64; its bundled `codex-cli` 0.162.0-alpha.17.2. Generated schemas from that bundled executable were inspected, particularly thread status, turn lifecycle, resolved requests, and blocking input. Schema generation did not start a model session.

## Evidence and choices

- [Official Codex IDE developer settings](https://learn.chatgpt.com/docs/developer-settings?surface=ide) documents `chatgpt.cliExecutable` and explicitly identifies it as development only. The installed manifest scopes it to the application and restricts it in untrusted workspaces. There was no contributed cross-extension activity API. Treat the proxy route as experimental, and recheck it on upgrades.
- [App-server protocol](https://learn.chatgpt.com/docs/app-server) documents stdio JSONL, turn lifecycle/outcomes, thread status, blocking approval/input requests, and request resolution. The observer reads that existing connection, not a separately started app-server. It injects no requests, alters no messages, approves nothing, and does not scrape the webview or parse private extension bundles.
- [Hooks](https://learn.chatgpt.com/docs/hooks) are unsuitable as the sole detector here: `Stop` can cause continuation, a `PermissionRequest` can be handled by another hook before user interaction, and hooks do not provide the required window identity. No hooks are installed.
- Status-item backgrounds use contributed fixed-default color identifiers and a guarded private `ALLOWED_BACKGROUND_COLORS` map in the extension host. Each window owns its item independently; no activity settings overrides are applied. The private capability is experimental, and its absence retains plain activity labels. See the [investigation](STATUS-ITEM-INVESTIGATION.md) for the mechanism and original rendered evidence.
- [VS Code public API definitions](https://github.com/microsoft/vscode/blob/main/src/vscode-dts/vscode.d.ts) expose `window.onDidChangeWindowState` and selection events with `Keyboard`, `Mouse`, or `Command` origins. There is no general click/keystroke observer for the full application. Only real unfocused→focused changes and Keyboard/Mouse editor-selection events are automatic acknowledgement signals. The `WindowState.active` property is a coarse activity/idle signal, not a reliable event for each click; timer-driven inactivity events must not acknowledge. The finished status item directly invokes the acknowledgement command as a one-click fallback. No proposed APIs or key interception are used.

## Modules and identity

`proxy.js` tees the IDE's existing bytes to/from the real bundled executable. `protocol.js` extracts minimal lifecycle events. `bridge.js` authenticates local connections and associates a direct parent PID with one UI extension host. `state.js` owns per-connection/per-thread activity and unread state. `status-appearance.js` renders the padded status item, checks private capabilities, and owns only its three registration entries. `legacy-recovery.js` uses the former `appearance.js` and `color-lease.js` solely to restore pending full-bar journals after upgrade. New activity never starts a watchdog or applies a settings overlay. `setup.js` guides profile bridge configuration in the existing window and distinguishes a missing connection from active monitoring. `extension.js` wires these modules to events and commands.

The launcher uses shell `exec`, preserving the IDE extension host as the proxy’s direct parent. On activation, this extension writes a mode-0600 registration for its own PID in a checked mode-0700 per-user temporary directory. The proxy only looks up its direct parent’s registration. It does not walk arbitrary ancestor processes or search by cwd. A non-IDE CLI invocation has no matching parent registration and cannot color a window. Codex must be in the same local extension host as this extension; split hosts/remote environments fail to disconnected rather than falling back to project routing.

A random source identity is assigned to every authenticated socket. Window reloads replace registrations/tokens and lose old unread state. Disconnection removes that source. Reconnection snapshots only live work, never historical success. Every snapshot and incremental message is ordered on one socket. Completed turn IDs are retained in a bounded duplicate suppression set; a delayed completion for another active turn is ignored. A new request gets a provisional pending entry, so a rejected submit cannot erase an existing running turn. No transcript polling, Codex process scanning, or idle-to-completion heuristic is used. Per-thread state is capped at 1024 threads per source and duplicate suppression at 2048 ended turns.

The local socket carries only lifecycle kind, thread/turn/request IDs, outcome, and waiting flags. Conversation content traverses the original stdio connection as required by Codex; the observer briefly buffers JSON messages in memory, bounded at 8 MiB per line, and does not persist content. Oversized lines cause monitoring to disconnect while byte forwarding continues. Socket output backlog beyond 1 MiB similarly stops observation. Same-user malicious processes are outside this local token’s security boundary; the token primarily prevents accidental/mismatched connections. There is no network listener or external service.

## Appearance ownership and upgrade recovery

The presenter checks the private map and expected built-in warning/error mappings before registering its three background identifiers. It contributes matching foreground identifiers with fixed defaults in dark, light, and both high-contrast themes. The built-in registrations are never replaced. Disposal removes only entries still equal to this presenter's own registered values. If another presenter has claimed one of its identifiers, it preserves that entry and falls back to an uncolored activity label. A rejected setter or unavailable capability is explained in diagnostics and the tooltip; there is no settings-based fallback.

The active item uses the prototype's 122 trailing spaces. Blue/purple use white text and amber uses black. Idle, disabled, and disconnected states remove the background and padding. Theme updates reapply the current presentation; explicit overrides of the contributed identifiers can change their defaults. The rest of the status bar/title bar is untouched. Sharing a project or workspace file no longer couples indicators or pauses activity colors, and an empty/unsaved window no longer needs an appearance settings target.

Upgrade recovery still computes the canonical path to the former `.vscode/settings.json` or saved `.code-workspace` target. Its temporary lease waits for any older host/watchdog sharing that target. When exclusive, it restores outstanding current and older generated-workspace journals with the former adapter's compare-and-restore semantics. This preserves unrelated user settings and newer edits. An invalid JSONC file or settings-cache mismatch retains the journal and reports pending recovery. Configuration events and lease changes retry recovery. Successful recovery releases the temporary lease; new activity creates no color journals or project settings files. A file/directory created by the old adapter is removed only when journal provenance proves ownership and it is empty. Surviving older builds can still apply their old overlays until reloaded.

The state machine acknowledges focus return synchronously and immediately updates the status item through its API. VS Code schedules the renderer update; no settings write is required. A completion arriving after focus returned follows the already-focused rule. Diagnostics retain up to 80 in-memory focus/state events without conversation content, alongside the current presenter capability and pending legacy recovery detail.

The existing authenticated socket also accepts a read-only diagnostics handshake. These clients are never registered as activity sources, and further messages on a diagnostics connection are ignored. `node scripts/diagnostics.js` queries live registered hosts concurrently, with bounded response size and timeouts. It reports unsupported old hosts explicitly rather than misrepresenting them as healthy. The GUI diagnostics command uses the same snapshot provider. Snapshots include the owning workspace and PID so output from different windows cannot be confused; automatic focus acknowledgements asynchronously record peer focus snapshots to expose contradictory focus reports. This instrumentation does not itself alter acknowledgement policy. Earlier diagnostics identified an inactive full-bar theme-color issue in the retired adapter. Version 0.2.0 instead renders independent status items.
